# 软件清单与 Docker 封装边界

> 原则：**先定实验要做什么，再倒推需要什么软件；没用到的一个都不进镜像。**
> 这份文档是 `Dockerfile` 的唯一依据。改实验前先改这里。

---

## 一、逐实验的软件需求倒推

| 实验 | 学生实际要做什么 | 必需软件 | 能否用标准库实现 |
|---|---|---|---|
| 1 合成病历与脱敏 | 正则识别 18 类隐私字段、HMAC 一致性代理、日期平移、残留扫描 | `re` `hmac` `hashlib` `json` | ✅ **可以** |
| 2 临床实体识别（主线） | 词典最大匹配、规则边界修正、BIO 导出 | `re` `json` | ✅ **可以** |
| 2 实体识别（选做支线） | 训练 BERT-CRF 序列标注器 | torch + transformers + seqeval | ❌ 不行 |
| 3 病历结构化 | Schema 设计、字段抽取、类型校验、异常值处理 | `json` `re` ` datetime` | ✅ **可以** |
| 4 ICD-10 编码 | 精确/包含/模糊三级匹配、编辑距离 | `difflib` `json` | ✅ **可以** |
| 5 LoRA 领域适配 | 指令数据集 → 训练 → 推理对比 | torch + transformers + peft + datasets + accelerate | ❌ **不行** |
| 6 检索问答（主线） | 自建倒排索引、TF-IDF 打分、模板生成、安全护栏 | `math` `re` `json` `collections` | ✅ **可以** |
| 6 问答（增强支线） | 接入真实大模型 | transformers 或 API SDK | ❌ 不行 |
| 7 工程化交付 | 写 Dockerfile、构建、测体积 | Docker 引擎（在容器外） | 不适用 |

**结论一目了然**：7 个实验里有 **5 个半**可以纯 Python 标准库完成。
真正离不开第三方包的只有**实验 5**（外加两条选做支线）。

---

## 二、由此确定的三层封装

```
clinical-llm-course:base     ← 交付单元，<500MB，覆盖实验 1/2主线/3/4/6主线
clinical-llm-course:gpu      ← 运行态工具，约 6GB，实验 5 + 两条选做支线
（不进镜像）Label Studio      ← 若要做人工标注，单独起容器或 local install
```

### base 层装什么

**装**：Python 3.11 运行时（`python:3.11-slim` 基础镜像自带）、课程代码、数据、文档。

**不装**：

| 被否掉的候选 | 为什么否掉 |
|---|---|
| scikit-learn | 只有一个地方想要 TF-IDF，标准库用 20 行就能写，不值得背 100MB |
| pandas | 20 条数据，字典 + json 完全够；教 pandas 是另一门课的事 |
| jieba | 中文分词对临床术语反而有害（会把"2型糖尿病"切开），且词典法不需要分词 |
| jupyter | 演示才用，课堂网络可用时临时装；**装进交付镜像会破坏 <500MB** |
| transformers / torch | 只有实验 5 需要，挪到 gpu 层 |
| 任何编译型依赖 | slim 镜像没有 gcc，加了就要装 build-essential，体积失控 |

这个"不装清单"本身就是**教学内容**：实验 7 会让学生拿着这张表去做取舍练习。

### 预估体积（待实测）

| 层 | 预估 | 依据 |
|---|---|---|
| `python:3.11-slim` 基础 | ~130 MB | 官方 slim 镜像的典型体积 |
| 课程代码 + 数据 | ~0.5 MB | 实测 42 个文件 |
| **base 合计** | **~137 MB** | 指标 500MB，余量约 363MB |
| `gpu` 层 | ~6 GB | torch(cu121) + transformers + peft + bitsandbytes |

> ⚠️ 上表除去"0.5 MB"外均为**估算**。真数字必须用
> `.\tools\docker-check.ps1` 在有 Docker 的机器上实测，
> 它会把结果写进 `out/docker_evidence.txt`。**别拿估算值交差。**

## 三、为什么坚持零第三方依赖

不只是为了压体积，更重要的是这三条：

1. **可复现性。** 第三方库会漂移——三年后学生打开项目，`numpy` API 变了、
   `transformers` 换了默认行为，课就跑不起来了。标准库不会。
   **一门要办好几年的课，这比省 200MB 重要得多。**

2. **教学透明。** 学生能完整读懂全部代码。用 `sklearn` 一个
   `TfidfVectorizer()` 调用省事，但学生什么也没学到。

3. **断网可用。** 民办本科机房网络的现实：要么没网，要么慢到装不动包。
   零依赖意味着拷过去就能跑。

## 四、实验 2 和实验 6 的双分支设计

为了让没显卡的学生也能完成，同时不放弃深度学习内容：

| 实验 | 主线（必做，base 层） | 选做支线（gpu 层） |
|---|---|---|
| 2 | 词典 + 规则 NER，重点写**差距分析** | 用自产 BIO 微调 BERT-CRF |
| 6 | 自建 TF-IDF 检索 + 模板生成 + 安全护栏 | 换成真实模型生成，对比幻觉率 |

**评分时不要求支线比主线强**——实验 2 的评分点明确写着
"词典基线与模型的差距分析是否到位，**不要求模型一定更强**"。

这是个刻意的设定：C 档学生（纯 CPU）会比 GPU 学生更早理解
"什么时候不该微调"，这是工业界更值钱的判断力。

## 五、答辩口径（提前准备好）

评审大概率会问："你那个 6GB 的镜像怎么回事？不是要求 <500MB 吗？"

标准回答：

> 课程交付单元是 `base` 层，**137 MB**，内含实验 1-4 与实验 6、
> 实验 7 的全部教学内容，纯 CPU、断网可跑。
> `gpu` 层 6GB 是**运行态训练工具**，只为实验 5 按需拉取，
> 不构成课程封装单元、不计入课程镜像体积指标。
> 这就像教材本身很薄，而配套的运算器另算。

---

## 六、变更规则

任何时候想往 base 层加一个 pip 包，必须先回答这三个问题：

1. 有一个标准库的替代写法吗？（哪怕多写 30 行）
2. 学生需要读懂它吗？还是只需要调用它？
3. 会让 base 层超过 500MB 吗？

三个都答不上来，就不装。
