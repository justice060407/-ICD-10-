# 实验 1 · 合成病历构造与脱敏管道

**学时**：6 学时 | **性质**：核心实验 | **对应岗位**：医学数据治理专员
**对应课程目标**：CO1、CO7 | **交付**：自写病历 5 条 + 脱敏管道改进 + 审计分析报告

---

## 一、你要做什么

分三步，难度递进：

1. **自己写 5 条虚构病历**（第 1-2 学时）——不是抄模板，是真的按临床逻辑编写
2. **跑通脱敏管道并读懂它**（第 3-4 学时）——理解 18 类隐私字段是怎么被识别的
3. **攻击你自己的脱敏结果**（第 5-6 学时）——扮演攻击者，找出漏网之鱼

**这个实验的关键不在代码写得漂亮，在于你有没有站在攻击者角度思考过。**

---

## 二、为什么从"自己编病历"开始

你可能会觉得：写病历不是医生的事吗？

正是如此——这个过程中你会被迫去理解**病历的内在结构**，而这个理解是后面
所有实验的地基。写完之后你会自然发现：

- 为什么主诉要短、现病史要长（信息密度完全不同）
- 为什么诊断写在最后但最重要（结构 ≠ 语义权重）
- 为什么年龄有时要写成"58岁"有时是"中年"（表达的多样性 = 抽取的难度）

这些都是后面写正则、写词典时会直接用到的认知。

### 步骤 2：编写 5 条病历

**硬性要求**：

- 5 条必须覆盖**至少 4 个不同科室**
- 必须有 1 条是**精神科/心理科**（你会发现它最难脱敏）
- 每条的 `sections` 六段都要写，主诉不超过 30 字，现病史不少于 100 字
- **`gold_icd10` 必须查**，不许瞎填。参考 `src/icd_map.py` 里的 `ICD10` 字典

> ⚠️ **虚构不等于随便编**。名字、电话、住址要**格式合法但内容虚构**。
> 特别是身份证号：写一个能通过校验位算法的假号，而不是随手按 18 个数字。
> 这是专业素养——你要造的是"看起来像真的假数据"，不是"一看就是假的假数据"。

### 步骤 5：扮演攻击者

现在换一个身份。假设你是拿到 `out_lab1/records_deid.jsonl` 的人，
你的任务是把这个人的身份认出来。检查清单：

| 攻击面 | 怎么查 |
|---|---|
| 年龄 + 科室 + 罕见病组合 | 一个人群里可能只有他一个人符合 |
| 医院名称保留 | 18 条里只有 2 条没被替换，看看是哪些 |
| 主管医师姓名 | 医师是全院公开的，等于半个人身标识 |
| 日期精确值 | 入院日期 + 出院日期能锁定到具体一次就诊 |
| 文本里没被替换的自由文本数字 | 比如"确诊 12 年"这类带时间的表述 |

用 grep 找找看有没有漏网的：

```powershell
Select-String -Path out_lab1\records_deid.jsonl -Pattern "\d{17}[\dXx]"        # 身份证样
Select-String -Path out_lab1\records_deid.jsonl -Pattern "1[3-9]\d{9}"         # 手机号样
Select-String -Path out_lab1\records_deid.jsonl -Pattern "\d{4}-\d{2}-\d{2}"   # 裸日期
```

找到命中就说明脱敏有漏。**把每一条命中记下来，这就是你的实验报告最有价值的部分。**

## 五、常见坑

| 坑 | 说明 |
|---|---|
| **正则括号写成捕获组** | `(19\|20)` 会被当作"要替换的部分"，结果只替换了开头两个字符，而残留扫描**查不出来**。必须写 `(?:19\|20)`。这是本管道历史上最危险的一个 bug |
| **宽泛规则覆盖精确规则** | 银行卡号是 `\d{16,19}`，身份证是 18 位，会互相吃掉。靠优先级解决 |
| **代理值保留了真实格式** | 如果把身份证替换成另一个 18 位数字，残留扫描器会**把自己生成的假号码又报警**。专用命名空间（`ID-DEID-`）+ 固定位宽才是正解 |
| **同一字段在不同通道算出不同代理值** | 见下方详解。本项目实测：**20 份病历里 13 份正文与头部的床号对不上** |
| **假替换：计数了但值没变** | 见下方详解。本项目历史上年龄曾"替换"20 处，**数值一个字没动** |
| **换 key 后结果对不上** | 这是设计使然：换 key = 换一整套代理值，用于跨批次隔离。别当 bug |
| 用真实医院名 | 虚构医院也要虚构，"示例市第一人民医院"这种写法是对的 |

### 两个必须亲手验证的坑

上面列的后两条是本管道 2026-10-07 实测抓出来的，**教科书上不讲，但项目里一定踩**。

**坑 A：同一字段算出两个代理值**

同一个字段会从两条通道进来：
结构化头部读到 `"12床"`，正文正则的捕获组只抓到 `"12"`（字符集里没有中文）。
两个不同的 `raw` → HMAC 摘要不同 → **同一张床得到两个不同的代理值**。
后果是下游没法把正文和结构化表关联起来，同一个人变成两个人。

管道自己的报告白纸黑字承诺了"相同原始值始终映射到同一代理值"，但这条承诺当时是**破的**，而所有指标依然显示"通过"。

根治办法是等于生成代理值之前先归一化：`SurrogateFactory._norm_id()` 剥掉非字母数字字符、纯数字再去前导零。

**验证**：改完再跑一次，统计正文与头部床号不一致的记录数。修复前 **13/20**，修复后 **0/20**。

**坑 B：假替换**

`age()` 原本只在 >89 岁时泛化，其余原样返回。于是 20/20 份病历的年龄数值一字未改，
审计日志照样记了 20 条，报告照样写"年龄：20"——**看起来做完了，风险原地不动**。

这比报错危险得多：报错你会去查，"通过"你不会。

现在默认泛化为年龄段（`58岁` → `45-59岁`），并保留 `--age-policy hipaa`
走 HIPAA Safe Harbor 口径（<90 保留原值）做课堂对比：

```powershell
python src\deid_pipeline.py --in my_lab1_records.jsonl --out out_lab1 --key "学号-lab1"
python src\deid_pipeline.py --in my_lab1_records.jsonl --out out_hipaa --key "学号-lab1" --age-policy hipaa
```

对着两份 `records_deid.jsonl` 看年龄字段，然后回答：**你的课程該用哪个口径？依据是什么？**

> 留一道思考：`45-59岁` 这种写法，残留扫描规则 `\b\d{1,3}\s*岁` 会不会把它误报成
> "精确年龄没脱干净"？去看 `src/deid_pipeline.py` 的 `_residual_scan()`，
> 想想为什么它没有误报——以及如果你将来加一条年龄残留规则，该怎么写。

## 六、思考题

1. **"残留风险记录数 = 0"能证明这份数据可以对外发布吗？** 给出你的判断和理由。
2. 如果把所有日期都删除（而不是平移），研究结果会损失什么？
   如果保留精确日期呢？**这个取舍谁有权决定？**
3. 你写的精神科病历为什么更难脱敏？如果这条记录泄漏，危害和其他科室一样吗？
4. HMAC 一致性代理保证了"同一个人全篇同一个假名"。
   这个特性在什么场景下是**优点**，在什么场景下反而是**漏洞**？

> 第 4 题是个真问题：一致性让你能做纵向研究，但也让跨文档关联攻击成为可能。
> 工业界的解法是"分批次换 key"，本课程 `--key` 参数就是为此设计的。
