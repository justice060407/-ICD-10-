# 实验 7 · 工程化交付

**学时**：2 学时 | **性质**：综合实验 | **对应岗位**：全员
**对应课程目标**：CO1-CO7 综合 | **交付**：自己的 Dockerfile + 一键复现脚本 + 体积实测

---

## 一、你要做什么

把你自己这一个学期做出来的东西，打包成一个**别人拿来就能跑**的镜像。

### 为什么这是最后一课

前六个实验你产出的都是"在你的电脑上能跑"的东西。
这不算交付。**真正的交付是：一个从没见过你电脑的人，也能复现你的结果。**

这一课同时是整个课程的收尾设计：你要回头看自己的代码，
这时候才会发现哪些地方偷懒写死了路径、哪些依赖没声明、哪些数据没放进去。

---

## 二、交付的标准（三条）

| 标准 | 检验方法 |
|---|---|
| **可复现** | 换一台机器，`docker run` 之后能跑出和你一样的结果 |
| **可验证** | 里面有一键脚本，不用看文档就知道怎么跑 |
| **够小** | base 层 < 500MB —— 这是本课程自己的硬指标 |

## 三、动手步骤

### 步骤 1：盘点你到底依赖了什么

这一轮把你前六个实验用过的东西列出来：

```
□ 标准库：re / json / os / sys / argparse / hmac / hashlib / difflib / math
□ 第三方：（列出你装过的每一个）
□ 数据文件：（你的任何 jsonl / json）
□ 环境变量 / 密钥：
```

然后问自己：**每一个第三方依赖，换成标准库要写多少行？**

参照 `docs/软件清单与封装边界.md` 的判定规则：

> 有一个标准库替代写法吗？学生需要读懂它吗？会让 base 超过 500MB 吗？
> 三个都答不上来，就不装。

### 步骤 2：写自己的 Dockerfile

根目录建 `Dockerfile.mine`：

```dockerfile
FROM python:3.11-slim

ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    LANG=C.UTF-8 \
    PIP_NO_CACHE_DIR=1

WORKDIR /app

# 先只 COPY 需要的东西 —— 这是减小上下文的第一道闸
COPY src/ ./src/
COPY data/ ./data/
COPY README.md .

CMD ["python", "src/run_pipeline.py", "--key", "my-course-2026"]
```

**三条要求**：

1. **不要 COPY 整个目录**。逐个写清楚，漏什么补什么。你会发现这逼着你理清楚项目的真实边界
2. **写 `.dockerignore`**。第一道坎就在这里：没有它的话，`out/`、`models/`、
   `.tmp/` 全都会被打进去
3. **用具体版本号**。不要用 `FROM python:latest`——明年 tag 会变，你的镜像就不可复现了

### 步骤 3：构建并测体积

在有 Docker 的机器上：

```powershell
docker build -f Dockerfile.mine -t my-clinical-course .
docker images my-clinical-course
```

记下 SIZE。**必须 < 500MB**。

超了的话用这个命令找出罪魁：

```powershell
docker history my-clinical-course
```

它会逐层列出每一层占多少。通常情况下你会发现是某个 pip 包干的。

### 步骤 4：一键复现脚本

写一个 `run_me.ps1` 或 `run_me.sh`，让别人不用读 README：

```powershell
Write-Host "正在复现《临床大模型与病历挖掘》课程实验..."
docker build -f Dockerfile.mine -t my-clinical-course .
docker run --rm -v ${PWD}/out:/app/out my-clinical-course
Write-Host "完成。产物在 out/ 目录。"
```

### 步骤 5：真换一台机器验证

这是本实验**唯一不可替代的一步**：找同学的电脑 / 实验室另一台机器，
用你的脚本从零跑一遍。

> 你会在这一步发现前六个实验里埋的所有雷 ——
> 硬编码的本机路径、忘提交的数据文件、没写进依赖清单的包。
> **把这些坑记录下来，比多写几百行代码更能体现你的工程能力。**

## 四、验收标准

| 检查项 | 权重 | 达标条件 |
|---|---|---|
| 依赖盘点 | 20% | 列出全部依赖，且对每个第三方依赖给出取舍理由 |
| Dockerfile | 25% | 用了 slim 基础镜像、COPY 精确、有 .dockerignore、版本锁死 |
| **体积达标** | 25% | `docker images` 实测 < 500MB，有截图 |
| 一键脚本 | 15% | 别人不用看 README 就能跑 |
| **换机验证** | 15% | 在另一台机器上成功复现，或记录下失败原因 |

## 五、常见坑

| 坑 | 说明 |
|---|---|
| `COPY . .` 一把梭 | 会把 `.git`、`out/`、临时文件全打包进去，体积失控 |
| `FROM python:latest` | 不可复现。slim + 具体版本是常识 |
| pip install 不锁版本 | 半年后装出来的是另一个版本的库，行为可能完全不同 |
| 忘了清 `/var/lib/apt/lists/*` | 白白多几十 MB |
| 在本机测试通过就交 | **本机通过毫无意义**，镜像里的环境和你本机不一样 |
| 认为"我这个需求必须用 XX 库" | 回去看第 1 步的规则，多数时候是没想过替代方案 |

## 六、思考题

1. 你的镜像里有没有一个依赖是"其实可以不用"的？如果有，当时为什么没砍掉？
2. "不可复现"的研究在学术上意味着什么？在商业上呢？
3. 三年后就装不出来的软件包该怎么办？你会怎么为一个"长期可复现"的需求做设计？
4. 如果你要让完全不懂技术的病案室老师也能用你的东西，
   除了 Docker 还能怎么做？Docker 是不是最优解？
